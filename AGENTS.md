# Project guidance

- This is a personal macOS 14+ application, built with Swift Package Manager and SwiftUI/AppKit. Python is the learning language.
- Build: `swift build`. Verify: `swift test`. Release: `swift build -c release`.
- Package with `bash scripts/package-app.sh`; launch with `open "dist/Python Teacher.app"`. Packaging builds release and verifies a local ad-hoc signature. `--universal` builds arm64+x86_64 (requires full Xcode).
- Share with `bash scripts/share-app.sh`: universal ad-hoc-signed app plus `scripts/HOW-TO-OPEN.txt`, zipped without extended attributes to `dist/Python-Teacher-<version>-macOS.zip`. There is no Developer ID/notarization; recipients clear Gatekeeper via Privacy & Security → Open Anyway or `xattr -dr com.apple.quarantine`.
- Branch naming: create a new branch before starting work, using a type prefix: `feature/…` (new functionality), `fix/…` (bug fixes), `docs/…` (documentation only), `chore/…` (tooling, build, packaging maintenance), `refactor/…` (no behavior change), `curriculum/…` (lesson/exercise content). Use short kebab-case names, e.g. `feature/shareable-app-package`.
- Runner compatibility tests can select an interpreter with `PYTHON_TEACHER_TEST_PYTHON=/absolute/path/to/python3 swift test --filter PythonRunnerTests`. Framework launchers are resolved to the actual executable; do not relax subprocess restrictions to accommodate launchers.
- Teacher providers (OpenAI Responses, Anthropic Messages, Google/xAI Chat Completions) are defined by `TeacherProvider`. All providers receive identical instructions, snapshots, prompts and schemas; only the wire format differs, and each stream accepts only its normal completion signal. Keys use per-provider Keychain items (`local.pythonteacher.<rawValue>`; keep the OpenAI service name stable). Changing the provider in Settings clears cloud consent.
- Tests use temporary learning stores and never require a live API key. Provider tests use URLProtocol mocks. Native rendering tests exercise SwiftUI/AppKit without requiring Accessibility automation.
- Capture native workspace screenshots with `PYTHON_TEACHER_UI_SNAPSHOTS_DIR=/absolute/path/to/output swift test --filter AppModelTests`; this includes all learning modes at default and minimum window sizes, reward states, player-progress and focus-session details. Standalone transparent SwiftUI views need an opaque background in snapshot hosts.
- Player XP is derived from saved learning/session evidence, never a mutable counter, and is distinct from chapter mastery. There is no gameplay level cap; keep threshold arithmetic overflow-safe. Focus tests inject `focusNow` and monotonic `focusClock`; restored unfinished sessions are paused and must not credit offline time.
- Exercise XP uses app-owned `ExerciseEffort` ratings snapshotted onto attempts. The user approved one-time historical recalculation in reward policy v2: analyze saved generated starter/reference ASTs in the restricted runner, apply reviewed ratings, back up the old progress file, and save atomically. Do not rewrite attempts during ordinary XP reads or award duplicate completions. Preserve missing-exercise history and fail without changing progress if analysis/save fails. Generated workload is the maximum of requested coverage and local structural work estimates, capped by `ExperienceRules.generatedUnitCap` (the chapter assessment's scope units, +1 for project scope, which replaced cumulative scope). The user approved a one-time reward policy v3 recalculation that applies the cumulative cap to saved generated exercises and generated attempt snapshots, including missing generated exercises; reviewed ratings are unchanged. Retain chosen difficulty, infer it only when absent, and label estimates. Never score learner code length or accept provider-awarded XP.
- Reward-effect snapshots cover deterministic animation phases and actual passing-solution feedback. Decorative overlays must never intercept input; AppKit `hitTest` expects points in the receiving view's superview coordinates.
- Keep PLAN.md updated with completion status and verification evidence. Do not mark unverified live API or GUI behavior as tested.
- Use synthetic/public learning data only. Keep API credentials in macOS Keychain, out of logs, files, generated exercises, and Python subprocess environments.
- Learner code execution must fail closed when sandbox restrictions cannot be applied; never fall back to unrestricted execution.
- No AI hints or solutions during chapter assessments. Progress is determined from explicit application rules and executable evidence, not model claims.
- Preserve unreadable saved progress rather than overwriting it with defaults.
- No third-party dependencies initially. The Swift tools-version directive is required package metadata.
- Assume the learner has no prior Python knowledge, regardless of technical experience. Explain new syntax and methods before requiring them; use small worked examples and plain-language numbered exercise steps with exact expected results and starter-editing guidance.
- Keep existing curriculum IDs and saved draft interfaces stable when revising teaching content. Incompatible foundation replacements use explicit `-v2` IDs; retain original definitions through `Curriculum.legacyExercises`, preserve version-specific drafts/assistance, share completion/review identity only through explicit `activityID` aliases, and exclude every assessment variant via `Curriculum.isAssessment`. Lesson code blocks are tested independently and must each run standalone in the restricted runner.
- Curriculum chapters form a prerequisite DAG with a single `basics` root; register chapters in topological order. Project practice uses only the transitive prerequisite closure plus the selected chapter as its toolkit, not every preceding array entry. Its required coverage is 1–3 current-chapter focus sections plus `project-integration`. Only the current chapter and its direct prerequisites are sent as full lessons. All generation scopes list the prerequisite closure as toolkit section titles. `Chapter.sectionRoles` marks headings as `.overview` (context only) or `.troubleshooting` (required only for the Debug format). Unlisted headings are practice, and section IDs stay positional. Whole-chapter XP counts format-independent `practiceTopics`. `Chapter.generationNotes` holds app-authored checking patterns; keep them consistent with the runner contract and free of assessment content. `ProjectBrief.catalog` briefs are synthetic, and each must name an existing `minimumChapterID`. A project with no brief requires a non-blank, untrusted objective in `scenario`. New chapter files live under `Sources/PythonTeacherCore/Chapters/`; exercise code and examples must remain Python 3.9-compatible and standard-library-only until the separate package-environment phase is approved. Run `swift test --filter 'CurriculumTests|CurriculumGraphTests'` for curriculum and graph verification.
- Learner text renders through `MarkdownContent` (`MarkdownContent.swift`). Supported: `#`/`##`/`###`, `- ` bullets, `1. ` steps, `> **Key idea:**`/`**Tip:**`/`**Watch out:**`/`**Note:**` callouts, ```` ```python ```` (executed by tests) and ```` ```text ```` (output box, not executed), inline `**bold**` and `` `code` ``. Wrap dunder names in backticks. Exercise instructions keep the exact `Goal:`/`Starting code:`/`Your task:`/`Expected result:`/`Check:` lines. Write short paragraphs, `###` steps, one action per numbered step and an output box after printing examples. Never add/remove/rename `#`/`##` headings (positional section IDs). `MarkdownDocumentTests` parses every curriculum text.
- Reading preferences (text scales, typeface, spacing, code size, paced/whole lessons) are device-local `@AppStorage` keys in `AppearanceKey`, injected by `appearanceEnvironment()`. Use `.appFont(_:)` instead of `.font(.textStyle)` in app views so interface scaling applies. Do not render `SettingsView` in tests (its `onAppear` reads the real Keychain); render `AppearanceSettingsSection` instead.
- Native keyboard tests using the AppKit responder chain must activate the test application and drain pending application events after showing the window; otherwise `NSApp.keyWindow` can remain nil despite `makeKeyAndOrderFront`. Activation can take multiple event-loop turns: use a bounded wait that drains events and reorders the window, then assert it is key. Native incremental find commits its match to the text view's selected range when focus leaves the search field.
- Teacher requests carry a fresh JSON workspace snapshot after bounded chat history. Send complete current code and runner-bounded output, with the source/operation/outcome of the latest run even when stale; never silently truncate workspace context. Reject snapshots above 256,000 UTF-8 bytes before recording a request or assistance. Optional per-message code fingerprints/run IDs preserve change comparisons across relaunch without duplicating code; execution evidence itself remains workspace-local and clears on navigation/reset/relaunch. Keep assessments and revealed solutions excluded, and never claim live model behavior was verified by request mocks.
